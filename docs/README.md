# Project Documentation

This is the canonical, human- and agent-readable context for the Jawaher Al Khair website project. Markdown files under `docs/` are the source of truth for project context — HTML planning artifacts produced during earlier discovery sessions are **not** canonical documentation and should not be relied on.

- **`architecture/`** — approved architectural context: [`blueprint.md`](./architecture/blueprint.md) (target architecture, boundaries, adapters, roadmap), [`architecture-decisions.md`](./architecture/architecture-decisions.md) (ADRs), [`technical-architecture.md`](./architecture/technical-architecture.md) (engineering-level spec: stack, repo structure, adapters in detail, API/DB/security/testing/performance), [`module-boundaries.md`](./architecture/module-boundaries.md) (module dependency-direction model), [`data-ownership.md`](./architecture/data-ownership.md) (domain model + data ownership matrix), and [`technical-decisions.md`](./architecture/technical-decisions.md) (what was decided/recommended/left open, plus the consistency-check log).
- **`requirements/`** — [`website-functional-requirements.md`](./requirements/website-functional-requirements.md): the product/UX-level functional specification, including the launch-vs-later classification and open business questions.
- **`ux/`** — how the customer experiences the site: [`ux-specification.md`](./ux/ux-specification.md) (principles, page/interaction behavior, priority matrix, implementation handoff), [`customer-journeys.md`](./ux/customer-journeys.md) (journey maps), and [`ux-decisions.md`](./ux/ux-decisions.md) (what was decided now vs. what's still open).
- **`design/`** — the bridge from the real brand identity to the website UI: [`design-system.md`](./design/design-system.md) (color/typography/logo tokens, layout, component visual language, motion), [`brand-to-ui.md`](./design/brand-to-ui.md) (extracted design language, product presentation, five category visual worlds, brand→UI mapping), [`design-decisions.md`](./design/design-decisions.md) (must-preserve rules vs. recommendations vs. open items, plus the consistency-check log), and [`asset-manifest.md`](./design/asset-manifest.md) (what's supplied under `_reference/` vs. still missing, naming conventions).
- **`planning/`** — material for planning stages not yet promoted into the documents above, including [`feature-completeness-audit.md`](./planning/feature-completeness-audit.md) (production e-commerce capability gap audit — what's covered, what's genuinely missing, classified MVP/production-required/later/out-of-scope/open-decision) and [`commerce-completeness-audit.md`](./planning/commerce-completeness-audit.md) (the equivalent deep audit for the Phase 4 commerce engine specifically — catalog, inventory reservation, cart, checkout, orders, payments, shipping, promotions).
- **`integration/`** — three phases of ERP integration work. **Phase 5** (`erp-integration-readiness.md`, `erp-data-ownership-matrix.md`, `erp-sync-map.md`, `erp-data-contract-outline.md`, `erp-integration-gap-analysis.md`) was written *before* any ERP codebase/database was available to inspect — kept for historical record, each now carries a Phase 6 pointer note at the top. **Phase 6** (`erp-discovery.md`, `erp-domain-map.md`, `erp-website-real-mapping.md`, `erp-inventory-analysis.md`, `erp-order-lifecycle-mapping.md`, `erp-shopify-integration-analysis.md`, `erp-integration-architecture.md`, `erp-integration-final-gap-analysis.md`) is the real ERP audit — the actual ERP codebase (`ERP JAW`), read directly, entity by entity, with file:line citations; this is the current source of truth for what the real ERP does. **Phase 7** (`erp-integration-implementation-plan.md` — start here — plus `erp-api-contracts.md`, `erp-integration-security-plan.md`, `erp-integration-failure-recovery.md`, `erp-integration-testing-plan.md`, `erp-integration-reconciliation.md`, `erp-website-admin-boundary.md`) is the final, implementation-ready design: target architecture, proposed API contracts, auth/RLS plan, failure-recovery/idempotency/retry strategy, testing plan, reconciliation strategy, and the Website-Admin-vs-ERP boundary — design-only, no code written. **Phase 8** (`erp-integration-foundation.md`) is the first phase that actually touches code in both repositories: the minimal service-to-service auth boundary (a real, working `/api/v1/integrations/website/health` endpoint in ERP JAW, verified by a real API key + connection id), the Website's `src/modules/erp-integration/` ERP Adapter/client foundation, request-id propagation, and a structured error contract — no catalog/inventory/customer/order/payment sync yet; read this document for exactly what exists today versus what's still planned. **Phase 8.5** (`erp-pre-integration-closure.md`) is the pre-integration closure gate: a full open-item register, live RLS verification (confirmed correctly forced on all 88 tables, app bypass by design per ADR-0001 — the platform's single largest prior open question, now resolved), a genuine end-to-end connectivity test against a real running ERP, Shopify/database-safety isolation checks, and the final, consolidated business-decision register — read this before starting any business-data integration phase. **Phase 9 / Step 9.0** (`catalog-inventory-gap-analysis.md`) is the Catalog & Inventory audit and field-level mapping — its key finding: the storefront UI (shop/category/PDP/search) still renders entirely from hardcoded mock data (`src/ui/commerce/mock-products.ts`), completely disconnected from the real, tested `catalogService`/Prisma stack, and the ERP has no read function that resolves weight-tier variant stock redirects (`stockSourceVariantId`) — both are named prerequisites before Catalog/Inventory sync can be built or would have any visible effect. **Phase 9.1** (addendum in the same `catalog-inventory-gap-analysis.md`, §16) closed the first prerequisite: `/shop`, `/shop/[category]`, `/product/[slug]`, and `/search` are now reconnected to the real `catalogService`/Prisma stack (mock data eliminated from all four), and single-SKU "Add to Cart" on the PDP now calls the real cart API — ERP is still not connected. **Phase 9.2** (addendum §17, same document) closed the second prerequisite, ERP-side only: a new `getSellableAvailability()` function (`ERP JAW/src/modules/warehouse/services/reservation.service.ts`) correctly resolves `stockSourceVariantId`/assembly-BOM redirects before computing availability, reusing the existing `resolveOrderLineComponents()` resolver rather than reinterpreting it — 15 new tests, tenant-isolation verified. **Phase 9.3** (addendum §18, same document, plus the dedicated [`erp-catalog-inventory-api.md`](./integration/erp-catalog-inventory-api.md)) built the actual ERP-side API boundary the Website will consume in a future phase: `GET .../catalog/products`, `GET .../catalog/categories`, and `POST .../inventory/availability`, reusing Phase 8's auth and Phase 9.2's inventory-resolution logic exactly, SKU-keyed (the Website has no `erpVariantId` column), with explicit documented omissions for open data-model gaps (variant label, media, currency) rather than fabricated values. No Website code was touched, and no Website sync/adapter was built yet — that remains the next, separately-reviewed phase. **Phase 9.3R** (addendum §19, same document) corrected a business-rule overreach the review caught: draft/publishing visibility was still an unresolved decision (§4/§9), so the catalog API's hard `400` rejection of an explicit `status=draft` request was removed (the safe default stays unchanged) rather than permanently foreclosing a future reconciliation process's ability to detect that gap. **Phase 9.4** (addendum §20, same document, plus the dedicated [`website-erp-catalog-sync.md`](./integration/website-erp-catalog-sync.md)) built the Website-side half of the boundary: a real ERP Catalog Adapter and Catalog Sync Service that populate `Category`/`Product`/`Variant` from the Phase 9.3/9.3R API — idempotent upserts keyed by stable ERP ids, a full-sync deactivation sweep, an incremental-sync foundation with a documented draft-detection gap, and a DB-native concurrency guard. **Phase 9.4R** (addendum §21, same sync document) corrected a review-caught identity gap: variant sync was matching on `sku` instead of ERP's own stable variant id, risking duplicate rows on a SKU rename — fixed by adding `Variant.erpVariantId` and re-keying on it, plus an explicit per-field ERP/Website/Derived ownership classification and a verified (not assumed) money/tenant-safety review. Catalog-only — inventory sync is explicitly not built yet and remains the next, separately-reviewed phase.

Before making an architectural or functional decision, read the relevant document here first. If a change conflicts with something already written, flag it rather than silently overriding it.

For how to actually run the project locally (install, dev server, tests, database), see [`../README.md`](../README.md) at the repository root — that file is developer-onboarding documentation, not project-context documentation, which is why it lives outside `docs/`.
