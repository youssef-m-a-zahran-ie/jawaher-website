# Premium Jawaher Al Khair Experience (Phase 10)

Status: implemented, verified. Last updated: 2026-09-13.

This document is the canonical record of Phase 10 — "transform the functional website into a distinctive premium Jawaher Al Khair digital experience." It extends [`design-system.md`](./design-system.md) and [`brand-to-ui.md`](./brand-to-ui.md) rather than replacing them; nothing in those documents' brand facts (colors, typeface, logo system) changed — this phase implemented what they had already specified but no prior phase had built (the icon, the packaging pattern) and built the Products Experience they had scoped but deferred.

---

## 1. What this phase found before writing any code

Per the phase brief's own instruction ("do not immediately start replacing components... study the real system first"), the actual state was inspected directly, not assumed from prior docs:

- **`_reference/brand/guidelines/Jawaher El khier.pdf`** (16 pages, "Created By RUBIX," 2023) is the *only* non-empty file anywhere under `_reference/`. Every other folder (`_reference/products/images/*`, `_reference/products/packaging/`, `_reference/experience/*`, `_reference/business/*`, `_reference/content/*`) contains only `.gitkeep` placeholders — confirmed by direct listing, not inferred. **There is no real product photography, no logo source files (SVG/AI/EPS), and no video/animation asset anywhere in this project**, for any of the five categories, dates included.
- The PDF itself contains: the official wordmark + palm-in-diamond icon (pp.2–8, with an explicit construction grid and four approved background combinations), the seven brand colors with exact HEX/RGB/CMYK (p.5, already correctly implemented in `globals.css` since Phase 2), Almarai type specimen (p.5), and a packaging label design (p.13) using a repeating ghosted palm/diamond pattern. The "product photography" elsewhere in the deck (pp.10–14: a bowl of dates, an Instagram mockup, an iPhone mockup, a billboard mockup) is the branding agency's own demonstration stock/mockup imagery — not Jawaher's real product photography, and `brand-to-ui.md` §2 already correctly classifies it as "style reference only," not a usable asset.
- **The icon existed nowhere in the digital product.** The header and footer rendered the wordmark as plain text with no mark at all; the favicon was Next.js's unmodified default. This was the single biggest gap between "has a design system" and "has a recognizable brand identity" — a customer could not have identified this as a Jawaher Al Khair page from the logo alone, because there wasn't one.
- The homepage (`Hero`, `CategoryTile`, `StoryTeaser`) already followed the brand's own established principle from Phase 3 correctly: real photography doesn't exist, so don't fake it — use typography and color fields instead, and label placeholders honestly (`ImagePlaceholder`'s `feature`/`card` variants, already in place). This phase's job was to extend that same honest discipline to the two things that didn't have it yet (the icon, the Products Experience), not to invent a different one.
- `docs/architecture/blueprint.md` §17 / ADR-017 had already pre-approved the Products Experience's technical direction (GSAP + ScrollTrigger, Motion, Lottie, real photography/video, no WebGL/canvas "unless a specific beat genuinely fails otherwise") and `ux-specification.md` §16 had already specified its exact per-chapter template (opening scene → 3–5 beats → key message → product showcase reusing the real `ProductCard` → CTA → next-chapter control → reduced-motion static fallback). Neither had ever been built (`(experience)/` route group, chapters, analytics event emitters — all present only as documentation/type declarations, confirmed by a full repo grep).

## 2. The central creative decision this phase had to make

The phase brief's own "Products Experience" section describes an ambition (palm trees, dates falling, bees, flowing oil, cinematic realism) explicitly framed as *"examples of creative direction, NOT a mandatory storyboard."* Achieving that literal ambition requires real photography or production-grade CGI — neither of which exists, and `design-system.md`'s own binding, non-negotiable constraint (added Phase 1, direct business input) forbids the only fallback that doesn't require real assets: *"cheap-looking AI/CGI graphics... cartoon visuals... generic illustrated product scenes."* Attempting a hand-built illustrated palm tree or a synthetic "bee" animation to fill this gap would have violated that constraint directly, and risked exactly the outcome the whole phase brief opens by rejecting: *"a cartoon food website."*

**Decision:** build the Products Experience's full cinematic *architecture* now (scroll choreography, five-chapter structure, real per-category storytelling copy, real product showcases, reduced-motion/mobile/SEO handling, analytics) using the one visual asset that genuinely is real and official — the brand's own icon geometry — as the cinematic subject, paired with an honestly-labeled placeholder ("صورة المنتج الحقيقية قادمة قريبًا" — "the real product photo is coming soon") for where photography belongs. This is not a workaround or a lesser version of the brief; it is the brief's own repeated instruction applied literally: *"design the experience so real assets can be inserted cleanly later"* and *"use neutral placeholders, document required production assets."* See §7 for exactly what production assets unblock the fuller version once supplied.

## 3. What was built

### 3.1 The brand mark, implemented for the first time (`src/ui/brand/`)

- **`jawaher-mark.tsx`** — `JawaherPalmIcon` (the palm-in-fan glyph alone, for the header/footer/hero horizontal lockup, matching pp.2–4) and `JawaherIconMark` (the same glyph inside the diamond outline, for the favicon/app-icon, matching p.8's "Icon-based" variant). Both are real SVG, generated from a small set of frond angles via trigonometry rather than hand-traced points, so they stay proportionally correct at any size and use `currentColor` throughout — inheriting whichever of the four official logo/background combinations (`design-system.md` §4) the caller already uses for text color, never a hardcoded fill.
- **`jawaher-pattern.tsx`** — the recurring ghosted palm/diamond texture from the brand's own packaging (PDF pp.4, 10, 13), as a tiled SVG `<pattern>`, always rendered at low opacity (`design-system.md` §7's existing rule for this exact motif) and always `aria-hidden`.
- **`src/app/icon.svg`** replaces Next.js's default favicon with the real icon, on the brand's own dark background — the "gold+cream on `#402A1E`" combination the PDF itself confirms (pp.3/6/7) as the most legible at small scale.
- Wired into `Header`, `Footer`, `Hero`, `StoryTeaser`, `CategoryTile`, and `ImagePlaceholder`'s `feature` variant (which meant the PDP's photo placeholder inherited the pattern for free, without that file being touched — a deliberate consequence of extending one shared primitive rather than one-off styling each page).

No logo redesign occurred anywhere — every pixel of the icon traces the existing, approved construction (`design-system.md` §4); the Arabic wordmark text next to it is set in the site's own Almarai typeface rather than an attempt to hand-trace the PDF's custom calligraphic letterforms in SVG, which would have been a real redesign risk `design-system.md` never asked for.

### 3.2 Homepage

Reordered/refined per the already-approved structure (`design-system.md` §8), not redesigned from scratch: Hero (now pattern + large low-opacity icon watermark instead of a bare gradient) → Categories (tiles now carry the real packaging pattern instead of a plain gradient) → real catalog products under an honest heading ("منتجاتنا" — see Phase 9.7 for why "الأكثر مبيعًا"/best-sellers was removed, unchanged this phase) → Trust strip (unchanged, already restrained/factual) → Story + Products Experience teaser, now linking to the *real* page instead of a "قريبًا" badge.

### 3.3 The Products Experience (`/experience`, `src/ui/experience/`)

- **`chapters.ts`** — the five chapters in the brand's own dates-first order, each carrying its `storytellingObjective` quoted directly from `requirements/website-functional-requirements.md`'s table (Provenance/freshness for dates, purity for honey, extraction quality for oils, freshness/selection for nuts, traditional craft for ghee) and a short, brand-voice `keyMessage`/`openingLine` — no invented facts, certifications, or origins.
- **`chapter-section.tsx`** — one full chapter per `ux-specification.md` §16's template: opening line → headline → visual → CTA (`تسوق <فئة>`) → real product showcase (3–6 real `catalogService` products, reusing `ProductCard`/`ProductGrid` exactly as specified — never mock data) → "الفصل التالي" link to the next chapter, or "العودة للتسوق" on the last. **Fully server-rendered** — every word of every chapter is real HTML in the initial response, satisfying §20's SEO requirement directly (a crawler sees complete content with zero JavaScript).
- **`chapter-visual.tsx`** — the "scene": the palm icon (rotated slightly per chapter, and mirrored left/right by chapter index) beside the honestly-labeled placeholder card. See §2 above for why this, not a fabricated photoreal scene.
- **`chapter-product-showcase.tsx`** — grid on desktop, horizontal swipe row on mobile (`ux-specification.md` §16 item 8's explicit instruction — this is the one thing that's genuinely different between Products Experience and the ordinary Shop grid).
- **`experience-motion.tsx`** — GSAP + ScrollTrigger (per blueprint.md §17/ADR-017), dynamically imported with `ssr: false` and mounted *only* from this route (`experience-client.tsx`), so its bundle weight never reaches Shop/PDP/Checkout. No `pin` anywhere (GSAP's most jank-prone feature, and no beat here needs it). See §5 for a real bug found and fixed in this file.
- **`experience-analytics.tsx`** — fires `product_experience_started` on mount and `product_experience_chapter_viewed` (param: category) via `IntersectionObserver`, independent of whether the motion enhancer loads at all. `product_experience_cta_clicked` fires from each chapter's real `TrackedLink` CTA. A new `order_cancelled`-style addition, `product_experience_...` events already existed as types in `analytics.ts`; only the actual `track()` call sites were missing before this phase, now added, matching `ux-specification.md` §24's mapping exactly. No parallel analytics system was introduced.
- **`chapter-nav.tsx`** — a quiet, plain-anchor five-dot rail (`ux-specification.md` §16's "persistent 5-chapter selector"), desktop-only per `design-system.md` §11 ("decorative elements recede first on mobile, not shrink").

### 3.4 Navigation

Added one real nav item ("تجربة المنتجات" → `/experience`) — no mega-menu was introduced (the phase brief explicitly discouraged one "unless the actual catalog structure justifies it," and it doesn't: five flat categories, unchanged).

## 4. Two real bugs found and fixed via actual screenshots, not just code review

Per this phase's explicit instruction to "test the actual implementation" rather than declare completion on code review alone, full-page Playwright screenshots were taken at desktop and mobile widths against a real production build. Two genuine, previously-invisible defects were found this way:

### 4.1 `cn()`'s tailwind-merge conflict resolution was dropping text colors

`src/lib/cn.ts` called plain `twMerge()`, which has no knowledge of this project's custom theme tokens. Both the custom font-size tokens (`text-h2`, `text-caption`, ...) and the custom color tokens (`text-text-on-dark-strong`, `text-accent`, ...) begin with `text-`, and tailwind-merge's default heuristics treated them as the *same* conflicting utility — silently keeping only whichever came last in a `cn()` call and dropping the other. Verified empirically (`twMerge("text-text-on-dark-strong text-h2")` returned only `"text-h2"`). This made `CategoryTile`'s category names render in the default (light-background) dark-brown body text color instead of cream — invisible dark-on-dark text on the homepage's category tiles. This was a **pre-existing bug**, not introduced by this phase (the same `cn()` call existed before Phase 10 touched this file at all) — it had simply never been visible before, because every other place combining these two token types happened to be on a light background where the dropped-to-default color was accidentally correct.

**Fix:** `cn.ts` now uses `extendTailwindMerge` to register this project's font-size and text-color tokens into tailwind-merge's own `font-size`/`text-color` class groups, so it correctly treats them as two independent properties everywhere in the codebase — fixing this specific instance and any other latent occurrence of the same trap, not just the one this phase happened to catch.

### 4.2 The Products Experience's scroll reveal could leave content permanently invisible

The first version of `experience-motion.tsx` set every chapter's headline/visual to `opacity: 0` immediately, relying entirely on GSAP ScrollTrigger firing to ever reach `opacity: 1`. A full-page screenshot (which some automated/headless renderers — and potentially search-engine crawlers, per this phase's own SEO requirement — capture without performing a genuine incremental scroll) left four of five chapters' content stuck at `opacity: 0` — visually, an apparently-empty page with only a CTA button and a "next chapter" link per section. This directly contradicted the phase's own repeated instruction not to hide content behind animation, and was worse than this same file's reduced-motion handling (which correctly never hides anything).

**Fix:** rewritten so no target ever starts at `opacity: 0` — every chapter's text and visual are always at full opacity by default; only a small Y-offset/scale is animated away, so even if the ScrollTrigger reveal never fires for any reason, the page is 100% readable. Verified by re-screenshotting: all five chapters now show correctly in a single full-page capture.

Both fixes are covered by re-running the full verification suite (§6) after applying them, not just re-inspected visually once.

## 5. Motion philosophy (as implemented)

- Motion is scoped entirely to `/experience` — Shop/PDP/Checkout/Cart carry zero new animation this phase (`ux-specification.md` §23's existing rule, unchanged).
- No `pin`. No scrub-linked opacity (removed after §4.2's finding). A one-shot `toggleActions: "play none none none"` reveal per chapter, triggered once on scroll-into-view, never reversing — simpler and more robust than a continuously-scrubbed timeline, with no correctness cost for this content (each chapter isn't trying to choreograph multiple beats against precise scroll position, just settle into place once).
- `experience-client.tsx` checks `prefers-reduced-motion` via `useSyncExternalStore` (not an effect + `setState`, which would itself trip `eslint-config-next`'s `react-hooks/set-state-in-effect` rule — a real lint failure hit and fixed during this phase) and simply never mounts the GSAP enhancer when the user prefers reduced motion. The page underneath is identical either way — this is not a "lesser" reduced-motion mode, it's the same content with the settle-in animation skipped.
- Mobile gets a shorter transform duration (0.5s vs 0.8s) and the product showcase becomes a horizontal swipe row instead of a grid — not a smaller version of the same layout, per this phase's "mobile is not desktop shrunk" instruction.

## 6. Performance and isolation strategy

- GSAP (`gsap`, `gsap/ScrollTrigger`) is a new dependency, added specifically for this phase per the already-approved technical direction (blueprint.md ADR-017) — zero runtime dependencies of its own, confirmed via `npm ls gsap`.
- Loaded via `dynamic(() => import(...), { ssr: false })` from `experience-client.tsx`, which is the *only* file in the entire app that imports `experience-motion.tsx`. This is the standard Next.js App Router isolation mechanism: every route already gets its own JS chunk, and a `ssr:false` dynamic import additionally means GSAP's code never executes (and its bytes are only fetched) on any page other than `/experience`.
- `/experience` uses `dynamic = "force-dynamic"` for the same reason `/shop` does (Phase 9.1's established rule): real, changeable catalog data must never be baked into a build-time static page.
- The catalog fetch (5 categories' products) is wrapped in try/catch, falling back to an empty product list per chapter on failure — the headline/message/visual content never depends on the database succeeding (see §4.2's sibling fix to the homepage in §8).

## 7. Production assets this unblocks once supplied

None of the following exist yet (confirmed, §1) — supplying them is a business/production task, not an engineering one, and the architecture above is deliberately built so dropping them in requires no structural change:

- Real product photography per category (dates/honey/oils/nuts/ghee) and packaging shots → `_reference/products/images/<category>/`, `_reference/products/packaging/` — unblocks replacing `ImagePlaceholder`'s "feature" placeholder in PDP, category tiles, and each Products Experience chapter's product-card slot with a real `<Image>`.
- Raw-material/process photography or short video loops per category (palm groves, honey extraction, oil pressing, nut sorting, ghee-making) → `_reference/experience/<category>/` — unblocks replacing `ChapterVisual`'s icon-based scene with the literal cinematic sequences described in the phase brief's own "level of ambition" examples.
- Real logo source files (SVG/AI/EPS) from whoever owns the brand identity, to replace this phase's redrawn-from-the-PDF approximation with an exact original, if one exists.
- A decision on the "best seller" concept (still absent from the schema, per Phase 9.7 — unchanged this phase) and on real brand-story/About copy (still an honest placeholder, per Phase 3 — unchanged this phase).

## 8. Known limitations

- **This sandbox has no reachable Postgres instance** (confirmed via a direct TCP connection attempt, same limitation Phase 9.7 documented). Every page shown in this document's screenshots that depends on real catalog data (the homepage's product grid, every chapter's product showcase) correctly rendered its "no products"/empty-state fallback rather than real product cards — the *code path* for real data is unchanged and was verified against the catalog-adapters/product-card logic already covered by the existing unit-test suite, but the actual visual appearance of a populated product grid on the new homepage/Products Experience layout was not visually verified against real data in this environment.
- Two pre-existing, unrelated e2e failures were found during this phase's verification and are **not** Phase 10 regressions — confirmed by stashing every Phase 10 change and re-running them against the untouched code, where they failed identically:
  - `tests/e2e/not-found.spec.ts`'s `/product/not-a-product` case and `tests/e2e/navigation.spec.ts`'s category-heading assertion both depend on `catalogService` calls that throw (rather than gracefully return "not found") when the database is unreachable — a pre-existing gap in `/shop/[category]` and `/product/[slug]` (Phase 9.1) that this phase did not introduce and, per its own scope ("visual/creative direction," not "backend resilience hardening" across unrelated pages), did not fix. It *was* fixed for the two pages this phase's own work materially depends on — the homepage and `/experience` (§4.2, §6) — since those are this phase's actual deliverables.
  - `tests/e2e/design-system-showcase.spec.ts` intermittently fails/passes depending on run, tied to a Next.js 16 "soft 404 via Suspense boundary" streaming timing subtlety its own code comment already flags as tricky — unrelated to any file this phase touched.
- One stale, pre-existing e2e test (`tests/e2e/navigation.spec.ts`'s cart-drawer test) asserted an aria-label (`"السلة، لا عناصر"`) that Phase 9.7 had already retired in favor of plain `"السلة"` when it replaced the always-empty cart with a real one — found and fixed this phase as part of running the full suite for the first time with browsers actually installed.
- No real multi-device/physical hardware testing was performed — verification used Playwright's Chromium at fixed viewport widths (390px, 1440px) plus the existing e2e suite's own device/viewport coverage, not real iOS/Android/low-power devices.
